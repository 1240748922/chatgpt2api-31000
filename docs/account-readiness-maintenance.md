# 3.2.31：账号可用性预评估与性能驱动的定期维护

这是完整就绪调度方案的**第一阶段**。真实改动包括定期维护放行策略，不只是增加统计界面；但本版还没有开启未知 AT 严格拦截、请求到来前的预热库存或跨实例刷新租约。

发布镜像：`ghcr.io/1240748922/chatgpt2api-31000:sha-471fc63`，应用提交 `471fc6345f93acaf26d78795d769da6edfd27f07`。[构建与发布已成功](https://github.com/1240748922/chatgpt2api-31000/actions/runs/35890716722)；更新命令和逐容器核验见 [版本说明](../VERSIONING.md)。

## 为什么导入时可以同步，平时却要低于 2 并发？

导入任务由独立 importer 分批入库。勾选同步后，它直接调用 `sync_accounts_and_quota()`；RT-only 导入先通过导入专用的请求槽位兑换 AT。这些主动导入操作不经过原来的周期任务低负载门控。

旧定期维护默认需要集群活跃生图不超过 2、等待请求为 0。这个限制是保护前台的保守策略，不是技术上无法边生图边同步。持续流量会让周期维护很久没有机会运行。

独立 importer 隔离了 HTTP 入口和部分线程池，**没有隔离共享数据库与上游网络**。本版保留其加速导入入口、批量写入、AT/RT/JSON 识别、弹窗和进度机制，没有给主动导入额外加上新门控。

## 界面与统计口径

概览中心和账号管理新增「账号可用性」面板，管理员接口为 `GET /api/accounts/availability`。没有公开凭据。

互斥主状态为：凭据就绪、有效期未知、有效期不足、AT 已过期、鉴权待核验、确认异常、已禁用。禁用优先于隔离，隔离优先于其他凭据状态；主状态数相加等于全池统计数。

- **凭据就绪**：本地能读到当前 AT 的到期时间，剩余时间大于 `max(基础窗口, 当前配置的请求预算 + 60 秒)`，并且未被标为异常、隔离或禁用。解析 JWT 声明不等于验证签名，也不能证明上游未撤销凭据。
- **文生图候选**：在上述就绪账号中，还满足现有账号状态和额度规则的数量。
- **图生图候选**：在文生图候选中再排除上传冷却账号。
- 候选数不按具体模型、套餐、来源、分片、出口或在途槽位过滤，**不是此刻保证可用的空闲并发数**；不取代现有概览的集群请求并发。
- 额度未知与有效期未知是两件事。保留原额度规则：没有远程确认耗尽时，不只因为本地 `quota=0` 就新增禁用。
- 「有 RT 可尝试恢复」不代表 RT 一定有效。「需补充凭据」是非就绪状态中没有自动刷新路径的数量。上传冷却、额度未知等补充指标不互斥，不能再次加到总数里。
- 账号行中的未知到期时间不再显示「AT 有效」，而是「AT 有效期未知」；凭据详情显示生图就绪预评估。旧接口的调度策略字段保持兼容。

界面每 15 秒刷新；后台统计缓存 5 秒。复制账号引用时短暂持有状态锁，解码分类在锁外进行；不会把这次统计接入每次生图的取号流程。刷新失败保留上次结果并提示，未知数字显示 `--` 而不是假装为 0。

本版是只读准入预评估。**现有 3.2.30 的凭据优先级、未知 AT 兼容行为和同步刷新兜底没有被悄悄替换成严格过滤。**

## 新定期维护调度

只改变 app0 单例生命周期 watcher 的鉴权核验、临期续期、未知额度同步、限流额度复查；不修改生图线程池、超分并发、模型或代理设置。

默认 `CHATGPT2API_ACCOUNT_MAINTENANCE_POLICY=performance`：

| 状态 | 行为 |
| --- | --- |
| 性能正常 | 允许小批维护，沿用原每批并发，默认 2，范围 1–8 |
| 部分指标偏慢 | 每次批处理调用只执行一批、每批 1 个，然后让出执行机会 |
| 样本不足 | 每次调用 1 个账号试探，不因冷启动无样本永久停机 |
| 明显过载 / 缺失实例 | 暂停启动新批次，不取消已在途任务 |
| 压力恢复 | 至少经过 10 秒观察，下一次检查再恢复 |

每批之前重新判断，集群采集有独立 2 秒缓存合并重复请求。每次批处理约 20 秒时间片，在批次之间检查预算；单个已开始的网络操作不强制中断，所以不是 20 秒硬超时。默认 watcher 周期间隔仍为 30 秒，可沿用原设置。一个周期有多个阶段，试探模式并不意味着整个周期总共只处理一个账号。

当前采样范围是应用实例 app0–app7：

| 信号 | 减速 | 暂停新批次 |
| --- | --- | --- |
| 进程 CPU / 可见 CPU 容量 | 75% | 95% |
| 容器/可见内存 | 80% | 95% |
| PostgreSQL 连接池已用 / 最大容量 | 80% | 100% |
| 数据库操作 P95 | 500ms | 1000ms |
| 账号写锁等待 P95 | 500ms | 1000ms |
| 请求入口排队 P95 | 1000ms | 单独此项不暂停，避免恢复任务饿死 |
| 账号查询 / OAuth 接口 P95 | 10000ms | 20000ms |
| 数据库 / 账号接口错误率 | 20% | 50% |

耗时/错误率使用最近 60 秒、每项最多 512 个样本，至少 3 个样本才按对应阈值判断。取最差实例，不能用健康实例平均值掩盖一个过载实例。数据库耗时包含 SQL 执行和凭据提交样本，不等于独立测量了全部连接池等待；池利用率是读取计数，不执行探测 SQL。

整个集群没有足够样本时先试探；已有近期有效样本且各实例资源健康后，空闲实例没有 SQL/OAuth 流量不会让全池永远停在单账号试探。资源报告缺失或实例未响应仍暂停，不能把失联解释成空闲。

鉴权 400/401、明确凭据失效不算系统超载错误；429、5xx、网络异常会计入错误压力。这里只度量账号查询和 OAuth，**上游生图几十秒不是维护系统过载的证据**。活跃生图数量仅展示：即使 300 并发，性能健康也不因为数字本身停同步；反之只有 1 个请求但数据库过载也会暂停新批次。

导入进程的独立 CPU/接口指标尚未汇入此面板，其共享数据库竞争可间接反映到应用数据库耗时；不声称已完整监控全部进程。本版也未把既有本地 single-flight/CAS 改成跨实例 RT 与生图互斥租约，不能据此宣称已消除跨实例刷新竞争。后台网络/数据库工作仍可能消耗资源，需要生产观测校准。

## 配置、升级与回退

新增环境变量已接入 Compose（不修改用户现有 `.env` 或 `config.json`）：

```env
CHATGPT2API_ACCOUNT_MAINTENANCE_POLICY=performance
CHATGPT2API_MAINTENANCE_DB_P95_MS=500
CHATGPT2API_MAINTENANCE_WRITE_WAIT_P95_MS=500
CHATGPT2API_MAINTENANCE_QUEUE_P95_MS=1000
CHATGPT2API_MAINTENANCE_UPSTREAM_P95_MS=10000
```

这些是减速阈值；除入口排队外，到两倍时暂停新批次。批宽继续由 `CHATGPT2API_MAINTENANCE_BATCH_CONCURRENCY` 控制，这不是生图或超分并发上限。

- 设置 `CHATGPT2API_ACCOUNT_MAINTENANCE_POLICY=idle` 并重建应用，可只回退周期账号维护到原低并发门控，保留统计面板。无数据库迁移。
- 注册补号、备份和清理继续使用原低负载策略及原有配置，没有一并放开。
- 混合旧版本实例没有完整新性能指标，会暂停新的周期维护批次；完成所有应用实例更新后恢复判断。新门控不会直接拒绝前台生图。
- 检查 `/version` 是 `3.2.31`，并核对容器 OCI revision。本版已完成构建发布，但不代表服务器已更新；Compose 默认标签是 `sha-471fc63`，仍允许 `.env` 覆盖。
- 前端统一使用新的资源版本后缀，避免入口与分包引用不同 Vue runtime。多数静态文件的 diff 仅此后缀，不是更换界面或改导入逻辑。
