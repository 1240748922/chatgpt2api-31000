# 3.2.35：缩短生图结果落库的账号写锁占用

## 运行证据

- 请求 `dc6de78a84d74055` 在首次取号阶段等待约 2.8 秒后报“all ready image account slots are busy”，未发起上游生成。
- 用户 18:28:19 的可用性详情：凭据就绪 2758，AT 过期 17724；图生图已知正额度账号 20 个，另有 2668 个额度未知；活跃生图 131。
- 维护明确显示“账号写锁等待较长”，每批 0 个：写锁 P95 3738ms，数据库 P95 143ms，账号接口 P95 2932ms。
- `writer_wait_ms` 采样的是进入 `AccountService._account_write()` 时等待进程内 `_write_lock` 的时间，不是图片文件锁、上游等待或单次 SQL 时间。3738ms 超过现有默认硬暂停边界 1000ms，因此续期/同步暂停。

以上证明暂停触发条件，不证明线上全部写锁耗时都来自同一调用。全局就绪数也不代表某个分片的空闲槽位。17724 个过期 AT 不等于 17724 个可恢复账号：没有有效 RT 或 RT 已确认失效的账号不能凭空续期。

## 复现与修改

1. 原有单后台结果写入器虽然合并同账号更新，但不同账号仍逐行进入串行锁、逐条事务提交。改为**每批最多 32 个账号**的 checked mutation，每批释放锁，批次之间让其他写入线程获得调度机会；不人为等待凑满一批。
2. 原有普通状态/额度冲突会在持有串行锁期间全池读取、解析、合并。改为只读受影响账号；发现旧身份缺失（可能远端删除/轮换）时仍回退原有全池身份协调，不能为了速度覆盖远端轮换或复活已删除账号。
3. 保留 affected-row CAS、额度扣减/计数合并、凭据代际保护、快照写入日志，以及“局部写入收据不能推进全池修订”的规则。落库使用最新内存状态，不回灌排队时的旧账号副本。
4. 包含 3.2.34 的首次全忙有界等待及取号诊断；不增加普通上游尝试次数，不放行过期/未知有效期 AT，不增加单账号并发。

未修改维护暂停阈值、导号接口/弹窗、预热策略、真实 `.env`、代理、超分、生图模型或数据库结构。不是禁用锁，也不是提高数据库连接数。

## 本地证据与复验

全部使用合成账号、临时 SQLite 和模拟上游，不使用真实账号或消费额度。

旧代码回归：100 条结果产生 100 次单行写入；普通单账号冲突读取整个 20002 行池。修复后前者最多 4 批、每批不超过 32 行，后者只读取受影响账号。测试还覆盖批次提交期间继续完成图片、远端删除/轮换、排队后本地删除、不提前确认其他账号未落库的结果。

一次额外的本机对照：20000 行池、16 条均发生状态冲突的结果，旧路径 16 次全池读取，约 16943ms，最长一次持写锁约 1126ms；新路径无全池读取，约 60ms，最长持锁约 59ms。两个版本的最终额度和成功计数均核验一致。**这是特定冲突场景的离线结果，不是线上延迟承诺。**

## 更新后观察

- 核实所有 app 和 importer 为 3.2.35 的同一应用 SHA，不能仅看 `latest` 标签；实际发布记录以 `VERSIONING.md` 为准。
- 在相近流量下对比写锁 P95、数据库 P95、维护每批数量、就绪账号数及首次取号失败比例。写锁样本窗口为 60 秒，另有 10 秒恢复观察；旧样本不会在修复后立即消失，维护还受周期调度和其他性能信号约束。
- 预期是减少大池结果写入争用，让指标回落后后台按原规则恢复。若写锁仍高，应继续查其他持锁路径；若 CPU/内存/数据库仍过载或指标缺失，维护仍会暂停。不保证一次更新就恢复所有过期账号或消除所有 503。
- 无需清锁文件、清租约表、重置额度或重新导入整个账号池。
