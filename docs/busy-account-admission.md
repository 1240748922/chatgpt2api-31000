# 3.2.34：首次取号繁忙时的有界等待

## 已确认的现象与边界

用户提供请求 `dc6de78a84d74055`：总耗时 3105ms，取号等待 2828ms，快照检查 83ms，`image_attempts=[]`，原始错误为 `all ready image account slots are busy`。它在本地取号阶段失败，尚未上传参考图或发起上游生成；不能据此判定全池额度已耗尽。

旧版本在“全忙”和“无候选”两种情况下共用约 2 秒等待。协议层已有的容量重试要求先出现一次上游尝试，因此首次取号的繁忙请求不会进入该重试。合成账号复现：唯一合法账号暂被另一请求占用，在短窗口之后释放；旧版本提前失败，新版本在预算内等到释放并完成一次模拟生图。

**本次没有证明线上槽位泄漏，也没有确定后台“暂缓同步”的触发指标。**全局可用性面板不是本次请求所在分片的空闲槽位数，需要保留下述诊断才能进一步区分分片不均、真实繁忙及异常占用。

## 改动

- 只对“存在就绪账号，但槽位全忙”延长等待，默认上限 30 秒，受请求总截止时间约束。释放槽位的通知会立即唤醒等待者，不固定睡满 30 秒。
- 独立配置 `CHATGPT2API_IMAGE_BUSY_WAIT_SECONDS`（0–120 秒；0 回退原短等待窗口）。无请求截止时间的内部探测仍保留原短等待。
- 空池、过期/未知 AT、上传冷却或远端确认额度耗尽仍沿用原短探测及错误判据；不为了减少 503 而允许无效凭据。
- 取号等待不算上游尝试、不消耗普通换号重试次数、不增加单账号或总生图并发；不跨分片借号，也不绕过共享租约。
- 取号事件保留 `account_wait_reason`、`account_shard_index/count`、`matched_count`、`ready_count`、`busy_count`、`limited_count`、`upload_limited_count`、`available_slot_count`、`selection_loop_count` 与 `selection_wait_ms`，包括零值及各次尝试日志。
- 不修改后台性能暂停阈值、导入/续期逻辑、代理、超分或存储流程；没有数据库迁移。

## 验证与继续排查

- 测试覆盖首次繁忙后成功、请求截止、繁忙上限、绝对等待边界不重置、真实空池/过期/耗尽快速返回、正常生成后的本地和共享槽位释放、原始日志与监控 API 保留诊断。
- 更新后在失败请求 JSON 的 `monitor.events` 中找 `image_local_rejected`，或成功取号的 `image_account_lookup`。分片索引从 0 开始；扫描计数只对应当前请求过滤条件，成功提前命中时不是完整库存统计。
- 若仍显示全忙，结合本分片 `ready_count/busy_count` 和实时在途请求判断，不要直接清零占用或删除共享租约表。
- 还需“账号可用性 → 详情”的暂停原因和性能指标，才能判断为什么待恢复账号没有及时恢复；本补丁不能创造额度，也不保证持续过载时永不报错。

镜像、应用 SHA 与更新方法以 `VERSIONING.md` 最新记录为准。
