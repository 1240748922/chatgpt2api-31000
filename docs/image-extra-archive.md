# 额外图片归档与注册来源恢复

## 对外返回与计数

- 保留每个请求槽位至多一张输出，`n=1` 对外仍只返回一张。
- 额外图片不进入公共 `data`、对外图片 URL 列表、画廊自动推送或成功张数。
- 已下载的额外图片原始字节交给后台归档，不进行额外超分，不再占用主请求保存的等待时间。上游图片下载过程不在本次修改范围内。
- 这不改变上游实际生成张数或上游扣额规则。

## 资源与异常处理

- 每个进程一个归档 worker，最多 16 个等待任务，总接收数为 17；运行中和排队图片字节合计上限 64 MiB。多个应用实例各有自己的上限。
- 入队操作不等待容量；满队列或超过字节预算时，仅把额外归档记为失败，主图仍然成功，不触发重新生图。
- 排队超过 300 秒的任务跳过保存；开始执行时使用独立 60 秒保存预算，而不是原请求的 deadline。底层正在执行的阻塞 I/O 仍受原存储实现超时约束。
- 正常停机取消尚未执行的任务并写入失败回执，等待正在执行的任务结束。异常断电时内存队列不保证恢复；日志中超过 420 秒仍无回执的项目显示归档中断，不冒充保存成功。
- 有待归档或归档失败的请求保留上游会话以便手动恢复；本次未增加后台账号调用或延迟删除上游会话。

## 日志与兼容

- 主请求日志立即记录归档 ID、槽位、排队状态及计数；归档完成后，管理员重新打开请求详情可看到额外图片。
- 回执存放于共享应用数据库的新表 `image_archive_results`，因此经网关落到另一实例仍可查看。只在日志详情按 ID 查询，不给账号筛选、概览统计增加扫描。
- 日志详情合并回执时，不改变请求成功状态、成功张数、主图 URL 或计费相关输出。
- 回执随日志保留期外加一天余量清理；已有图片沿用原图片保留策略。
- 注册来源设置初次读取失败后，可直接重新保存，或点击“刷新状态”再保存；持续失败会显示具体错误，不会静默启动旧来源。
- 未更改账号导入/续期/预热策略、注册邮箱实现、代理配置、Compose、Nginx、镜像标签或版本号。

## 回退

回退本次源码即可恢复原同步保存行为；新增表是附加元数据，旧版忽略它，无需删除账号、图片或数据库表。上线前仍应按原部署流程备份。
