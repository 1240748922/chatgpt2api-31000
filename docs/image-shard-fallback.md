# 就绪账号分片不均与 503（3.2.47）

## 线上证据

2026-10-07 北京时间 20:47:42–21:07:22 的只读日志样本共 182 条请求：91 成功、87 条 `503 / no_available_account`、1 条 429、1 条 502、2 条 400。8 个应用实例均已运行 3.2.46，容器未重启或 OOM；采样时并非生图并发占满。

503 平均约 2.18 秒结束，`image_attempts` 为空，原始原因是 `no image account is ready for current model/status filters`。例如 `4938e1813ffb40fe` 来自分片 3，匹配 799 个账号但 `ready_count=0 / busy_count=0`；`613d8db560f642f9` 来自分片 6，匹配 848 个账号但同样没有就绪账号。尚未上传或提交生成，问题发生在本地取号。

全局约 1930 个严格凭据就绪账号无法供空分片使用：旧取号逻辑按管理 ID 固定分片，始终排除其他分片，直到本地等待超时。分片 3、6 的账号实际已过期，放松请求有效期余量不能解决。监控的 `account_shard.ready_accounts` 旧口径只检查状态/额度，没有检查 AT 有效期，进一步掩盖了不均衡。

## 修改范围

- 本分片候选优先，仍使用原有预热、额度优先和轮转逻辑；本分片可以取得账号时不扫描其他分片。
- 本分片没有可用候选（包括本地忙、过期、额度或上传限制）时，严格模式且共享凭据协调器可用的请求可查找其他分片。候选必须通过相同的凭据有效期、套餐/来源、上传冷却和排除名单检查。
- 借用后必须通过现有数据库凭据租约才能派发。跨实例共享账号并发上限、RT 刷新隔离、上传冷却及当前凭据代次检查；数据库操作仍在本地账号锁外进行。截止后取得的租约立即释放。
- 未启用严格模式、没有共享协调器、以及后台页面预热均保留本分片行为。不重写账号管理 ID，不迁移数据库，不修改导入/续期/超分/并发配置。
- `account_shard.ready_accounts` 按严格有效期和本地凭据阻塞检查修正，仍为本分片候选预览，不能当作全局空闲槽位或实时上游余额。
- 请求日志增加 `account_shard_fallback`（0/1）、`account_selected_shard_index`、`local_matched_count`、`local_ready_count`、`local_busy_count`。原来的总扫描计数在兜底时合并两个不重叠范围；成功时提前停止，不能当作全池盘点。原 `account_shard_index` 继续表示处理请求的实例分片。

## 复验

先用合成账号和临时 SQLite 在旧代码复现空分片 503 及错误的就绪统计，再测试跨分片成功、本分片优先/忙、全部限流、套餐/来源/有效期/排除名单、共享上传冷却、RT 刷新隔离、并发争抢、截止释放及日志投影。真实 PostgreSQL CI 增加 8 个协调器同时争用一个账号槽位，只能一个成功的回归。所有测试均不调用真实生图。

## 更新后观察

更新方式与镜像标签见 [发布记录](../VERSIONING.md)。服务器由用户更新，确认所有应用实例为 3.2.47 后，观察原分片 3/6 是否出现 `account_shard_fallback=1`、`account_selected_shard_index` 指向其他分片并进入上游生成，比较最终 `no_available_account` 比例。

该修复使各分片共享已有就绪容量，不增加额度，不恢复无效 AT/RT，也不保证消除上游 429、生成失败或全局真实无可用账号时的 503。历史失败任务不会自动重跑。非本分片取号会增加一次候选扫描和现有共享租约竞争；正常本分片快路径保持不变。
