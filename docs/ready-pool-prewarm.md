# 3.2.32：严格就绪池、跨实例刷新协调、请求前页面库存

## 本版做了什么

- 可用性区域改为四个摘要卡片；状态细分、维护压力和预热统计放进定高、可关闭的详情窗，不再撑长概览。
- 默认严格准入：仅派发 AT 有效期已知、覆盖 `max(300秒, 剩余请求预算+60秒)` 的候选。过期、未知、待核验账号不会让客户请求同步兑换 RT。
- 后台续期包含有效期未知且有 RT 的账号；仍按性能压力小批运行，先恢复凭据再核验普通额度。无 RT 或新 AT 仍没有可解析有效期的账号不会伪装成就绪。
- 新增 PostgreSQL/SQLite `credential_runtime_gates` 表：单凭据短事务共享生图租约与刷新互斥。手动、后台、故障恢复、RT-only 导入共用刷新发送保护；不在网络期间占数据库连接或全局账号写锁，不改变账号集合修订号。
- 刷新响应不明确、落库失败、进程消失后，发送记录保持隔离，不靠租约过期再次兑换旧 RT。详情显示“续期结果待确认”，需核对新凭据或补充新的 RT；**不要删除该表来强行重试**。
- RT 导入先复用已管理账号的同一 RT；原 AT/RT/JSON 识别、原导入弹窗、批量保存和任务断点继续保留。
- 每个应用实例提前为少量本分片就绪账号 GET 首页，保存独占 Session、Cookie、设备指纹和页面协议资源。真正请求到达时优先使用库存账号，重新领取权威租约和出口后，一次性领取匹配上下文。
- 预热不创建业务会话、不获取/缓存 requirements 一次性令牌、不预扣图片额度、不占生图槽。未命中立即冷启动；保留原上传与首页初始化重叠优化。
- 后台维护的压力采样加入独立 importer，避免只看到 app 空闲却忽略导入进程占用数据库。

## 配置与容量口径

| 环境变量 | 默认 | 作用 |
| --- | ---: | --- |
| `CHATGPT2API_STRICT_IMAGE_CREDENTIALS` | 1 | 严格派发与共享刷新保护；0 为全实例统一回退兼容模式 |
| `CHATGPT2API_PAGE_PREWARM_TARGET` | 16 | **每应用实例**库存目标，0 关闭，最大 512 |
| `CHATGPT2API_PAGE_PREWARM_TTL_SECONDS` | 45 | 本地保守库存 TTL，5–120 秒；不是上游承诺 |
| `CHATGPT2API_PAGE_PREWARM_WORKERS` | 8 | **集群总**补货线程，按已有分片静态分配，最大 64 |
| `CHATGPT2API_PAGE_PREWARM_RATE` | 8 | **集群总**补货启动速率上限/秒，按分片分配，最大 256 |
| `CHATGPT2API_MAINTENANCE_IMPORTER_URL` | Compose 配置 `http://importer:80` | 额外维护压力来源，内部接口要求已有集群密钥 |

8 个 app 默认合计最多 128 个闲置上下文。库存、补货线程不等于生图或超分并发上限，未命中不排队。指标减速/暂停时不继续补货；首版不根据 CPU 低就扩大网络压力。

代理/出口配置、凭据代际、显式指纹不匹配会丢弃库存；TTL 到期关闭 Session。已领取上下文不再回池。使用 `use_thread_local_curl=False` 顺序交接同一个 curl handle，禁止并发访问；本地真实 HTTP keep-alive 测试验证跨线程仍是同一连接。上游随时可能关闭连接，不能保证每次免握手，也不能加速实际模型生成时间。

现有生图、超分、上传重叠、导入并发和代理配置未降低，也不覆盖服务器真实 `.env` 或 `config.json`。

## 互斥与失败边界

- 领取时按 AT 索引读取当前权威账号，只检查这一行，不加载全池。调度缓存不能越过数据库中已轮换、禁用或待核验的状态。
- 生图租约覆盖剩余总预算加 120 秒清理余量，正常结束/失败释放确切租约。释放暂时失败不丢弃已经生成的图片，保守等租约到期；现有请求截止机制仍必须生效。
- RT 发送保护按 RT 的 SHA-256 资源标识及凭据代际区分，不存原始 AT/RT。成功先保存账号/导入检查点，再结束发送保护；明确 OAuth 拒绝按原错误策略处理。
- 所有参与进程必须运行本版、共享同一数据库并使用同一严格准入设置。不能混跑旧进程后宣称具有完整互斥保证。新建表是可重入增量迁移，旧账号数据不重写；旧版不会使用新表。
- JWT 本地 `exp` 只是准入信息，不代表已验证签名或保证未撤销。远端明确的鉴权拒绝仍优先。普通额度同步也不是 AT 有效期证明。
- 存在大量未知/过期账号时，严格就绪数会低于总账号数；没有足够就绪容量仍然有界等待/报错，不无限重试、不保证任何请求都成功。
- 预热库存只在内存，重启后重建。图片下载、超分、持久保存和历史存储锁逻辑没有在本次替换。

## 可验证的指标

- `/api/accounts/availability`：`policy=strict`；凭据状态、文生图/图生图候选及本实例预热 `ready/target/hit/miss/expired/failed`。候选不是实时空闲槽位，最终还需满足模型、来源、分片、额度和实际请求预算。
- 请求日志 `account_credential_lease_ms`：权威复核及共享租约耗时，包含在等待账号内。严格正常请求不应出现前台 `account_token_http_ms`。
- 步骤事件 `page_prewarm_hit=1/0`：命中或冷回退；`page_prewarm_age_ms` 是上下文年龄，**不与本次耗时相加**。
- 本地测试覆盖跨实例刷新/使用交错、未知凭据恢复、模糊失败禁止重兑、精确释放、原导入/导航/弹窗、预热身份失配和真实连接交接。发布工作流使用独立 PostgreSQL 17 运行数据库交错测试，通过后才构建推送镜像。

## 首次从 3.2.31 升级

先拉取发布记录指定的镜像。暂停外部新请求并停止新导入，等待在途生图和导入完成，再统一重建 app0–app7 与 importer，最后恢复网关。不要在旧实例还有在途请求时先开启新后台刷新，旧实例没有共享租约记录。

部署时不删除数据卷，不重建 PostgreSQL。建议先备份数据库和配置；新表在启动时创建，PostgreSQL DDL 有跨进程启动互斥。

不适合严格准入的凭据来源，可统一将 `CHATGPT2API_STRICT_IMAGE_CREDENTIALS=0` 回退原兼容派发；这也会退出本版的共享发送保护，需要全实例统一生效。只关闭预热使用 `CHATGPT2API_PAGE_PREWARM_TARGET=0`，不必回退账号安全逻辑。

具体应用 SHA、构建成功链接和升级命令以仓库 `VERSIONING.md` 的最新记录为准。
