## 可复现的阻塞路径

旧版后台快照刷新虽然不持有账号调度锁进行 I/O，却仍持有 `_write_lock`：

```
占写锁 → 查询版本 → 读取全池 → 解析/规范化 → 深拷贝 → 合并发布 → 解锁
```

凭据刷新 HTTP 已经完成时，`_apply_refreshed_tokens()` 仍必须拿同一把写锁
才能同步保存新 AT/RT。大账号池的读取/解析、数据库连接等待都可能把凭据
保存挡住；即使没有手动导号，其他实例更新额度也会触发快照刷新。

新增真实线程 + 临时数据库回归：分别暂停后台版本读取和快照读取，在不放开
暂停点时执行一次凭据轮换到生图结果的完整测试路径。旧版两项均失败，前台
保存必须等后台释放；修复后前台凭据已落库、生图流程已完成，后台仍在暂停。
该复现证明存在此阻塞路径；生产日志没有锁持有者字段，不能断言所有锁等待
都只来自快照，也不能承诺每条请求固定减少 7–10 秒。

## 修改与一致性保护

新流程：

```
不占写锁：查询版本 → 读取全池 → 解析/规范化 → 深拷贝
短暂占写锁：对齐并发提交 → 合并未落库的使用量 → 发布快照
```

不能简单挪锁后直接覆盖缓存，否则旧快照会把刚刷新的凭据、导入或删除状态
覆盖掉。本次增加仅在快照读取期间存在的内存写入记录：

* 每个变更行记录其数据库事务版本及已落库值/删除状态。只记录真实写入或
  权威重读覆盖的行；批量参数中未修改的行不能冒用其他行的提交版本。
* 快照 SELECT 之后的本地提交补入快照；已经包含在 SELECT 中的旧提交不覆盖
  快照里的更新远端状态。AT/RT 轮换、别名和占用槽位保持一致。
* 未落库的成功计数/额度变动继续合并一次，不丢失、不重复扣减。
* 全池缓存版本仍使用全池 SELECT 的版本，不能用局部写入版本跳过远端导入。
* 缺少可排序事务版本时不猜先后，放弃这次旧快照发布、保留当前状态并稍后重读。
  快照成功、失败或放弃后清除内存写入记录。

AT/RT 仍同步事务落库，账号真正的写操作仍串行且执行原 CAS 校验。没有删除
凭据保护、跳过保存、改变刷新策略，也没有把保存无条件丢给后台。

## 诊断细项

保留 `account_token_write_wait_ms`，新增其中两项：

* `account_token_writer_lock_ms`：账号写入串行锁等待。
* `account_token_dispatch_lock_ms`：账号状态锁等待，包含提交后重新取得状态锁。

两者是原等待总项的子项，不能再次累计到请求总耗时。这样仍有阻塞时可以区分
等待其他写入与等待状态合并，而不是继续增加账号或超分并发。
